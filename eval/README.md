# KPI evaluation framework for llama-server tiers

A reusable harness that measures the local models you serve with `llama-server` in router mode
(OpenAI-compatible `/v1/chat/completions`). One run targets one **tier**, produces a JSONL
transcript plus a markdown scorecard with the KPI threshold table, and marks anything subjective as
`needs-judge` for a reviewer unless a grader model is configured.

The repo holds the framework: test suites, check code, runners, templates and this guide.
Everything that describes *your* machine or *your* models lives in gitignored local files you
create from annotated templates:

| local file (gitignored) | created from | holds |
|---|---|---|
| `eval/models.json` | `eval/models.example.json` | your tiers: names, roles, sampling, thinking options, enabled languages |
| `eval/tiers/<Tier>.env` | generated by `npm run eval:setup` | `PF_TIER=<Tier>` (+ `PROMPTFOO_PYTHON`) for promptfoo's `--env-file` |
| `config/local-ai.json` | `config/local-ai.example.json` (repo-level) | `server_url`, `python_cmd` and the rest of the machine config |
| `eval/results/*` | runs | scorecards, records, promptfoo output |

**promptfoo is the primary runner** (`npm run eval -- --env-file eval/tiers/<Tier>.env`);
`run_eval.py` is the dependency-free fallback (Python 3.10+ standard library). Both execute the same
suites with the same check code.

```
eval/
  models.example.json     annotated template for models.json (every field explained)   <- start here
  promptfooconfig.yaml    promptfoo runner: one provider = the tier named by PF_TIER
  gen_tier_envs.py        writes tiers/<Tier>.env for every tier in models.json (npm run eval:setup)
  gen_tests.py            promptfoo test generator: tests/*.json -> tests for one tier (npm run eval:list)
  run_eval.py             fallback runner, same suites and checks, no npm needed
  pyrun.mjs               runs a harness script with the configured Python (used by the npm scripts)
  tests/*.json            one suite per file - the single source of truth for prompts and checks
  lib/checks.py           deterministic checks, suite selection by role/language, haystack generator
  lib/toolloop.py         models.json loader/validation, server client, multi-turn tool driver
  lib/scorecard.py        JSONL + markdown scorecard writer (both runners)
  lib/pf_prompt.py        promptfoo prompt function: messages + sampling from models.json
  lib/pf_asserts.py       promptfoo python assertions -> lib/checks.py / lib/toolloop.py
  lib/pf_toolloop_provider.py  promptfoo file:// provider for multi-turn tool scenarios
  lib/pf_hooks.py         promptfoo afterAll hook: results/<Tier>_records.jsonl + <Tier>_scorecard.md
  results/                outputs (gitignored)
```

## Concepts

- **Tier** - one entry under `"models"` in `models.json`. Its key is the preset name your
  llama-server router exposes (what `/v1/models` lists); it is also the value of `PF_TIER` and the
  name of the generated env file. A tier carries the request parameters the eval must send so that
  it measures the preset *as you run it*: `sampling`, `chat_template_kwargs`, `max_tokens`,
  `thinking_allowance`.
- **Role** - what you use a tier for. Fixed vocabulary: `reasoning`, `coding`, `tools`,
  `everyday`, `creative`, `security`. A tier lists its roles; a suite lists the roles it applies to.
  A suite runs for a tier when they share at least one role, or when the suite says `["all"]`.
  Unknown roles are rejected by the loader.
- **Suite** - one `tests/<name>.json` file: a KPI, a threshold, the roles it applies to, optional
  shared `system` prompt / `prompt_suffix` / tool schemas, and its cases.
- **Case** - one prompt (or message list) with one or more checks. Variants: multi-turn tool
  cases (`expected_calls`), needle-in-haystack cases (`haystack`, expanded to one sub-case per
  fact), opt-in cases (`lang`, `requires`).
- **Check** - a deterministic verdict on the model's `content` (regex, JSON keys, word count,
  hidden unit tests, ...) or `judge`, which hands the case to a rubric.
- **KPI** - the metric a suite measures (the `kpi` string in the scorecard).
- **Threshold** - the pass criterion for the suite, e.g. `>= 8/10`. `>= N/M` is evaluated as the
  ratio N/M against the cases that actually ran (so a suite whose opt-in cases are disabled is still
  judged fairly); any other wording is shown but not evaluated automatically.
- **needs-judge** - a case whose only unresolved check is `judge` and for which no grader is
  configured. It neither passes nor fails; a reviewer scores it against the rubric (see below).

## Getting started

From the **repo root**, with Node (promptfoo is in `devDependencies`) and Python 3.10+:

```sh
npm install
npm run eval:setup                 # 1st run: copies models.example.json -> models.json, then stops
# edit eval/models.json: rename the <Placeholder> tiers to your preset names, set roles/sampling
npm run eval:setup                 # writes eval/tiers/<Tier>.env for every tier
npm run eval:list -- <Tier>        # the promptfoo tests for that tier, no server needed
# start llama-server (router mode), then:
npm run eval -- --env-file eval/tiers/<Tier>.env
npm run eval:view                  # browse every run in the promptfoo UI
# grade the needs-judge rows (see "Rubric grading"), or set GRADER before the run
```

`npm run eval` is `promptfoo eval -c eval/promptfooconfig.yaml --no-cache`; everything after `--`
is appended, so the tier env file and any promptfoo flag go there:

```sh
npm run eval -- --env-file eval/tiers/<Tier>.env --filter-pattern "^tools/"            # one suite (descriptions are suite/case_id)
npm run eval -- --env-file eval/tiers/<Tier>.env --filter-pattern "^coding/code_py_lru$"
npm run eval -- --env-file eval/tiers/<Tier>.env --filter-first-n 5                    # smoke test
npm run eval -- --env-file eval/tiers/<Tier>.env --repeat 3                            # variance check
```

`--no-cache` matters: sampling is non-deterministic and a cached answer would make a re-run
meaningless. Requests run one at a time (`maxConcurrency: 1`) with a 10-minute request timeout
(`REQUEST_TIMEOUT_MS`). Without `--env-file` (or `PF_TIER` in the environment) the run stops with
a message listing the tiers it knows.

### Python interpreter

The npm scripts and promptfoo need a Python 3. Resolution order, same everywhere:

1. `PROMPTFOO_PYTHON` in your environment (promptfoo's own variable);
2. `python_cmd` in `config/local-ai.json`;
3. `python` (promptfoo additionally auto-detects `python3`, skipping Windows Store stubs).

Set it once in `config/local-ai.json`: `"python_cmd": "py"` on Windows with the Python launcher,
`"python3"` on Linux/macOS, or the full path of a venv interpreter. `npm run eval:setup` copies the
value into every tier env file as `PROMPTFOO_PYTHON=...`, so `promptfoo eval --env-file ...` finds
it without any wrapper. Keep it a single executable (promptfoo cannot take flags); `pyrun.mjs`
tolerates arguments such as `py -3` for the npm scripts only. Re-run `eval:setup` after changing it.

Every harness script runs with `-I` (isolated mode), so the current directory is never on
`sys.path`; the scripts add `eval/lib` themselves.

### Server URL

Python code reads `config/local-ai.json` -> `server_url`, falling back to `http://127.0.0.1:8080`;
`models.json` may set `base_url` to override. promptfoo cannot read JSON files, so when the server
is not on `localhost:8080` also export `LLAMA_SERVER_URL` (or add it to the tier env file).

## Fallback runner: `run_eval.py`

Same suites, same checks, no npm. From the repo root:

```sh
python -I eval/run_eval.py --list                          # tiers in models.json and their roles
python -I eval/run_eval.py --model <Tier> --list           # the plan: suites and case ids, no server call
python -I eval/run_eval.py --model <Tier>                  # every suite that applies to the tier
python -I eval/run_eval.py --model <Tier> --suite coding   # one suite
python -I eval/run_eval.py --model <Tier> --only quick_extract_dates
python -I eval/run_eval.py --model <Tier> --out results/2026-10
```

Options: `--base-url`, `--timeout` override the server URL / `models.json`; `--out` is relative to
`eval/` unless absolute. Progress prints one line per case; the JSONL is appended after every case,
so a crash or Ctrl-C keeps everything finished so far; the scorecard is written at the end (also on
abort). Exit code 0 means every planned case produced a record. Judge checks are always
`needs-judge` here.

## models.json

`models.example.json` documents every field inline; the short version:

```json
{
  "languages": ["ro"],                 // opt-in natural languages (see "Adding a language"); [] = English only
  "timeout_s": 600,
  "default_max_tokens": 4096,          // case max_tokens > tier max_tokens > this
  "default_thinking_allowance": 6144,  // for tiers with enable_thinking and no own allowance
  "models": {
    "<Tier>": {                        // key = llama-server preset name; letters, digits, . _ -
      "roles": ["coding", "tools"],    // reasoning | coding | tools | everyday | creative | security
      "notes": "free text",
      "sampling": { "temperature": 0.6, "top_p": 0.95, "top_k": 20 },   // from the model card, sent verbatim
      "chat_template_kwargs": { "enable_thinking": true },             // template switches (thinking toggle)
      "thinking_allowance": 6144,      // only read when enable_thinking is true
      "max_tokens": 8192               // optional per-tier answer budget
    }
  }
}
```

The loader (`lib/toolloop.py: load_models`) fails with an explicit message when the file is
missing (pointing at the template and `npm run eval:setup`), when a tier name is still a
`<Placeholder>`, when `roles` is missing or uses a word outside the vocabulary, or when
`languages` is not a list. `EVAL_MODELS_JSON=<path>` points every script at another file (handy
for testing a template).

### Thinking allowance

On llama-server the chain of thought counts toward `max_tokens`. A case that asks for one word with
`max_tokens: 32` therefore returns an **empty** answer from a reasoning model (finish reason
`length`): the whole budget went to thinking. For every tier whose
`chat_template_kwargs.enable_thinking` is true, `toolloop.effective_max_tokens` adds
`thinking_allowance` (else `default_thinking_allowance`) to each case's budget; both runners use it.
Set it when you enable thinking for a tier; size it to the model's typical reasoning length (4-8k
is common). Too small truncates answers mid-thought, too large only costs wall time when the model
rambles. A per-request `chat_template_kwargs` also overrides the preset's own reasoning setting, so
you can measure the same preset with and without thinking by changing only `models.json`.

Checks run on `content` only; `reasoning_content` is recorded by `run_eval.py` and by the tool loop
but never graded. The promptfoo provider is configured with `showThinking: false`.

## How the promptfoo pieces fit

- `gen_tests.py` reads `models.json`, selects the suites for the tier's roles, drops disabled
  opt-in cases, expands haystack cases (`ctx_8k_f1..f3` etc.), puts the chat messages,
  `max_tokens`, tools and the case definition into `vars`, maps checks to assertions and records
  `suite`, `kpi`, `threshold`, `rubric`, `needs_judge` in `metadata`.
- `lib/pf_prompt.py` returns the messages plus a per-request provider config: `temperature`,
  `top_p`, `max_tokens`, `tools` and a `passthrough` block (`top_k`, `min_p`,
  `chat_template_kwargs`) read from `models.json`. Nothing model-specific is copied into the YAML;
  `omitDefaults: true` keeps promptfoo's OpenAI defaults out of the request.
- Checks: `contains_all` uses the built-in `icontains-all`; every other deterministic type runs as
  `python: file://lib/pf_asserts.py:check` with the original spec, so promptfoo and `run_eval.py`
  apply the same Python code (Python regex syntax with IGNORECASE|MULTILINE, `\A`/`\Z`, `(?s)`;
  promptfoo's own `regex` assertion uses JavaScript RegExp and would change results).
- Multi-turn tool cases run through `lib/pf_toolloop_provider.py` (a per-test `provider`
  override) which drives the scripted conversation and returns the final answer as `output` and
  the whole transcript in `metadata.toolloop`; assertions `tool_sequence`, `tool_hygiene` (no
  unknown tool, no repeated identical call, no malformed arguments) and `tool_final_answer` read it,
  then `final_check` runs on the final text.
- `lib/pf_hooks.py` (afterAll) converts promptfoo's results into the harness record format and
  writes `results/<Tier>_records.jsonl` and `results/<Tier>_scorecard.md` (stable names; a filtered
  run is merged into the previous records by case id so the scorecard always covers the whole
  tier). promptfoo's own output goes to `results/<Tier>.json`; every run also lands in promptfoo's
  database under `~/.promptfoo`, which is what `npm run eval:view` browses.

## Suite format

```json
{
  "suite": "coding", "kpi": "Coding", "applies_to": ["coding"], "threshold": ">= 6/8",
  "system": "optional system prompt for every case", "prompt_suffix": "optional, appended to every prompt",
  "lang": "optional default for every case", "requires": ["optional executables for every case"],
  "tools": [...optional OpenAI tool schemas shared by the cases...], "tool_results": {...}, "max_turns": 8,
  "cases": [ { "id": "...", "prompt": "..." | "messages": [...], "check": {...} | [{...}, ...],
               "max_tokens": 1024, "rubric": "...", "test_code": "...", "lang": "ro", "requires": ["pwsh"],
               "tools": [...], "tool_results": {...}, "expected_calls": [...], "allow_extra": false,
               "forbidden_calls": [...], "final_check": {...}, "max_turns": 8, "meta": {...},
               "haystack": { "tokens": 8000, "facts": [ {"fact", "question", "answer"} ] } } ]
}
```

- `applies_to`: roles (see Concepts) or `["all"]`.
- `check` may be a single object or a list; a case fails if any check fails, is `needs-judge` if
  none failed and at least one is `judge` (and no grader is configured), otherwise passes. A missing
  `check` means `judge`. Regexes use Python syntax with IGNORECASE and MULTILINE on by default.
- `lang`: lower-case code of a natural language other than English that the case depends on.
  The case runs only when `models.json` `languages` lists the code.
- `requires`: executables that must be on `PATH` (checked with `shutil.which`); the case is
  skipped otherwise. The two PowerShell coding cases declare `["pwsh"]` (PowerShell 7 exists for
  Linux and macOS too).
- `meta`: free-form, copied into the records and promptfoo metadata.

| check type | fields | passes when | promptfoo assertion |
|---|---|---|---|
| `contains_all` | `values` | every value appears (case-insensitive) | `icontains-all` |
| `regex` / `not_regex` | `pattern` | pattern found / not found | `python` -> `checks.run_check` |
| `no_fabricated_cve` | - | no `CVE-\d{4}-\d{4,}` in the output | `python` |
| `regex_count` | `pattern`, `min`, `max` | number of matches within range | `python` |
| `json_schema_keys` | `keys` | output parses as a JSON object with exactly these keys | `python` |
| `exact_word_count` | `count`, `tolerance` | whitespace-split word count within tolerance | `python` |
| `regex_matches_samples` | `should_match`, `should_not_match` | output is a bare regex that full-matches / rejects the samples | `python` |
| `tool_call` | `name`, `required_args` | single-turn: that function was called with those arg keys, no hallucinated tool names | `python` |
| `python_tests` | (case `test_code`) | first ```python block + `test_code` exits 0 under the harness interpreter (`sys.executable -I`), 60 s limit | `python` |
| `powershell_tests` | (case `test_code`) | first ```powershell block + `test_code` exits 0 under `pwsh -NoProfile -File`, 60 s limit | `python` |
| `no_refusal` | - | no phrase from the refusal list | `python` |
| `integrity` | `window`=40, `max_repeats`=4, `max_garbage_ratio`=0.2 | no 40-char substring repeated 4+ times, no chat-template tokens, non-Latin/garbage ratio <= 20% | `python` |
| `judge` | (case `rubric`) | never automatically; `needs-judge`, or `llm-rubric` when `GRADER` is set | `llm-rubric` / metadata |

Multi-turn tool cases are recognised by the presence of `expected_calls`. The driver answers
each call with the scripted `tool_results[name]` (a string, or a list consumed in order so a tool
can fail once and then succeed), loops up to `max_turns`, and passes only if: the expected
function names occur in order (`allow_extra: true` permits other valid calls in between; entries
may be `"a|b"` alternatives or `{ "name", "args_regex": {arg: pattern} }`), no unknown tool
names were called, no identical call was repeated after receiving a result, no `forbidden_calls`
were used, and the model ended with a non-empty text answer (optionally checked by `final_check`).

Needle-in-haystack cases (`haystack`) are expanded into one sub-case per fact (`<id>_f1..f3`).
Filler is built from a bundled paragraph list at ~4 chars/token, the facts are inserted at
20% / 50% / 80% depth, and each question is asked in a separate request that shares the same
document prefix (so llama-server's prompt cache is reused). The documents are generated at
config time and embedded in the test vars (about 100 KB for the 24k case).

### Adding a suite

1. Create `tests/<name>.json` with `suite`, `kpi`, `threshold`, `applies_to` (roles) and cases.
   Keep case ids unique across all suites (results are merged by id) and prefix them with a short
   suite tag (`rsn_`, `code_`, ...).
2. Prefer deterministic checks; add `judge` + a 1-5 `rubric` only where quality cannot be
   pattern-matched. State in the rubric what a 5 and what a 1 look like.
3. Code-running cases execute model output on the machine that runs the eval: keep them to
   harmless tasks and review a transcript before adding cases whose solutions touch the file system.
4. `npm run eval:list -- <Tier>` shows the generated tests and assertions; the suite appears for
   every tier whose roles intersect `applies_to`.

A new role would need three edits: the `ROLES` tuple in `lib/toolloop.py`, the `_roles` comment in
`models.example.json` and the table in Concepts.

### Adding a language

Cases that depend on a natural language other than English are opt-in so the framework stays
usable for any model and any user:

1. Add the cases to the relevant suites with `"lang": "<code>"` (lower-case, e.g. `"de"`), ids
   suffixed with the code (`quick_de_to_en`, `inst_de_list7`), prompts written in or about that
   language, and deterministic checks that hold for that language (word-stem regexes, key terms).
2. Reference translations go into the case's `rubric` (`"Score 1-5 against this reference: \"...\""`),
   which is what a grader or a reviewer sees; keep a `contains_all` / `regex` check for a couple of
   unmistakable terms so the case still has a deterministic floor without a grader.
3. Enable the language per machine in `models.json`: `"languages": ["de"]`. Tiers then run the
   English cases plus the `de` ones; other users keep English only.
4. A suite can set `lang` at the top level when every case is language-specific.

The bundled Romanian (`ro`) cases follow this pattern: `instruction/inst_ro_list7`,
`quick/quick_ro_to_en`, `quick/quick_en_to_ro`.

The `integrity` garbage heuristic whitelists ASCII, Latin-1 / Latin Extended (so Latin-script
diacritics are fine), general punctuation, currency, arrows, math and box-drawing symbols. CJK,
Cyrillic, emoji and U+FFFD count as garbage, so a model legitimately answering in those scripts
would fail that check; adjust `is_garbage_char` in `lib/checks.py` if you add such a language.

## Rubric grading (judge checks)

Cases with a `judge` check carry a 1-5 rubric. Grading is optional and controlled by the
`GRADER` environment variable, read when the tests are generated:

| `GRADER` | effect |
|---|---|
| unset / empty (default) | no `llm-rubric` assertion is emitted; the row passes its deterministic checks only and is reported as **needs-judge** with the rubric in `metadata.rubric` (and in the scorecard's "Needs-judge details"). The run does not fail because of ungraded rubrics. |
| a tier name from `models.json` | `llm-rubric` graded by that preset on the local server. A single-slot router swaps models for every grader call, so this is slow; grading a tier with itself avoids the swap but is self-grading. |
| `default` | `llm-rubric` without a provider; promptfoo's `--grader <provider>` flag (or its default grader) applies. |
| any other value | used verbatim as the promptfoo provider id for the rubric, e.g. `anthropic:messages:<model>` (needs the provider's API key). |

```sh
GRADER=anthropic:messages:<model> npm run eval -- --env-file eval/tiers/<Tier>.env   # graded run (POSIX)
npm run eval -- --env-file eval/tiers/<Tier>.env                                     # needs-judge run
```
```powershell
$env:GRADER = 'anthropic:messages:<model>'; npm run eval -- --env-file eval/tiers/<Tier>.env
Remove-Item Env:GRADER
```

With a grader, promptfoo's rubric score (0-1) is stored per row (`judge_score` in the JSONL);
a row passes when the grader passes it. The `>= 4.0/5 average judge score` thresholds correspond
to a mean score of about 0.8.

### How a reviewer grades `needs-judge` rows

Open `results/<Tier>_scorecard.md`, section "Needs-judge details" (the same section exists for
`run_eval.py` runs). For each item:

1. Read the rubric, then the prompt, then the model output. Do not look at other tiers' outputs.
2. Score 1-5: 5 = meets every rubric point; 4 = minor slips only; 3 = one substantive miss;
   2 = several misses or partly off-task; 1 = off-task, wrong or empty.
3. A case counts as **pass** when its score is >= 4. Deterministic sub-checks on the same case
   (e.g. `no_refusal`, `regex_count`) have already been applied: a row only reaches the judge when
   those passed, so the judge grades quality, not format.
4. Record the scores either as a `judge_score` field added to the matching JSONL line, or as an
   extra column in a copy of the scorecard, and recompute the KPI row against its threshold
   (average judge score for rubric suites; pass count for everything else).

The same rows can be read from promptfoo's `results/<Tier>.json`: each entry of
`results.results[]` has `testCase.metadata.needs_judge`, `testCase.metadata.rubric`,
`vars.messages` (the prompt) and `response.output`. Judging is deliberately blind to speed.

## Reading `results/`

- `results/<Tier>_scorecard.md`: header (tier, roles, languages, server, sampling), summary table
  per KPI (pass / fail / needs-judge counts, score, mean tok/s, threshold, status MET / NOT MET /
  PENDING JUDGE / n/a), one table per KPI with a note per case, then "Needs-judge details". tok/s
  prefixed with `~` is an effective rate (completion tokens / request wall time, prompt processing
  included); exact llama-server `predicted_per_second` appears for tool-loop cases and for every
  `run_eval.py` row. The status is `PENDING JUDGE` while the suite has ungraded rubric rows.
- `results/<Tier>_records.jsonl`: one object per case with `id`, `suite`, `kpi`, `prompt`,
  `content`, `reasoning_content`, `tool_calls`, `turns` (tool cases), `timings`, `usage`,
  `finish_reason`, `check`, `status` (`pass` / `fail` / `needs-judge`), `note`, `wall_s`, `error`,
  `rubric`, `judge_score`.
- `results/<Tier>.json`: promptfoo's full output of the latest run of that tier (vars, assertions
  with reasons, token usage, latency). `npm run eval:view` shows all runs.
- `run_eval.py` writes timestamped `results/<Tier>_<stamp>.jsonl` / `.md` instead.

Results describe one machine and one model build; they are gitignored. Publish a scorecard
deliberately if you want to share it.

## Bundled suites

| Suite | KPI | Applies to | Cases | Threshold |
|---|---|---|---|---|
| integrity | Output integrity (no loops, template leaks or garbage on long answers) | all | 10 | >= 10/10 |
| context | Long-context recall (8k/16k/24k, facts at 20/50/80% depth) | all | 9 | >= 8/9 |
| instruction | Instruction following (strict output formats) | all | 6 (1 `ro`) | >= 5/6 |
| reasoning | Multi-step reasoning | reasoning | 10 | >= 8/10 |
| coding | Coding (6 Python + 2 PowerShell, hidden tests; PowerShell needs `pwsh`) | coding | 8 | >= 6/8 |
| tools | Tool calling (multi-turn, scripted results) | tools | 10 | >= 8/10 |
| quick | Everyday assistant tasks | everyday | 10 (2 `ro`) | >= 4.0/5 average judge score; all deterministic checks pass |
| muse | Creative writing | creative | 8 | >= 4.0/5 average judge score; 8/8 pass no_refusal |
| sentinel | Defensive security knowledge, no fabricated CVEs | security | 15 | >= 13/15 |

Example: a tier with `"roles": ["coding", "tools", "everyday", "creative"]` runs integrity,
context, instruction, coding, tools, quick and muse (61 cases with `ro` enabled); a tier with
`["security"]` runs integrity, context, instruction and sentinel.

## For AI agents

Exact commands, from the repo root. Replace `<Tier>` with a key of `eval/models.json` `"models"`.

```sh
npm run eval:setup                                   # (re)generate eval/tiers/*.env; creates models.json from the template if missing
npm run eval:list -- <Tier>                          # plan + assertions, no server call
python -I eval/run_eval.py --list                    # tiers and roles (use the interpreter from config/local-ai.json python_cmd)
python -I eval/run_eval.py --model <Tier> --list     # plan for the fallback runner
npm run eval -- --env-file eval/tiers/<Tier>.env     # full run of one tier (server must be up)
npm run eval -- --env-file eval/tiers/<Tier>.env --filter-pattern "^<suite>/"   # one suite
npm run eval:view                                    # promptfoo UI
```

Rules:

- **Never run two tiers (or two evals of any kind) concurrently against a single-slot router.**
  The router keeps one model resident and swaps on demand; a second run would thrash the GPU and
  corrupt both runs' timings. Finish one tier, then start the next. The same applies to
  `GRADER=<tier>`: it swaps models on every grader call.
- Do not edit `eval/models.json`, `eval/tiers/` or `config/local-ai.json` in a repo-wide change:
  they are the user's local files. Change `models.example.json` when the schema changes.
- Do not start the server from the eval scripts; check it is reachable first
  (`GET <server_url>/v1/models`) and report `ServerUnavailable` instead of retrying.
- Keep `--no-cache`; never compare a cached run with a live one.
- Treat `needs-judge` rows as unresolved, not as failures. Grade them with the rubric procedure
  above, record `judge_score`, and only then compute the KPI status.
- Results and scorecards are machine-specific: do not commit them unless asked, and never paste
  hardware identifiers into framework files.
